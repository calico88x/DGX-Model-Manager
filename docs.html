DGX Model Manager · v2.0.0 Reference

Secure, Compose-first model operations.

DGX Model Manager v2 is an authenticated control plane for local models, serving engines, LiteLLM, diagnostics, access control and optional multi-node DGX Spark operation. It manages infrastructure; it does not proxy inference traffic itself.

DGX Spark / GB10Docker ComposeTLS + RBACHugging Face + OllamaLiteLLM authMulti-node optional
01 · Architecture

How the stack fits together

The browser talks to the manager over authenticated HTTPS. The manager talks locally to model storage, service APIs, Docker Compose and optional remote DGX agents. Inference clients continue to use LiteLLM or direct engine APIs; Model Manager stays out of the latency-sensitive token-generation path.

Browser
  │ HTTPS + session + CSRF
  ▼
DGX Model Manager
  ├─ Hugging Face / Ollama
  ├─ LiteLLM
  ├─ Docker Compose
  ├─ host diagnostics
  └─ optional DGX node agents

Inference clients ─────────► LiteLLM / serving engine
Reachability is not ownership. v2 may detect an external engine as Online without gaining authority to stop it.
02 · Upgrade safety

Test v2 beside the current app

The default v2 installation is isolated: HTTPS port 8091, service model-manager-v2.service, config under ~/.config/dgx-model-manager-v2, and application state under ~/.local/share/dgx-model-manager-v2.
Install separatelyExtract or clone v2 into its own directory.
Run bash setup.shCreate the venv, local config, bootstrap TLS material and optional independent systemd service.
Open https://<dgx-host>:8091Create the first Admin using the one-time host-local bootstrap token.
Validate before promotionExisting serving workloads can remain externally managed while v2 is tested.
03 · Models

Existing storage stays in place

Hugging Face models are referenced in their existing cache rather than copied. Inventory understands Safetensors headers, SentenceTransformers layouts, multimodal configs, base-model metadata and quantized derivatives.

MetadataBehavior
Task / modalityUses local structure first; remote Hugging Face tags are supplementary
ParametersExact Safetensors counting for non-quantized checkpoints; quantized derivatives can resolve the base model
Dtype / quantizationBase dtype, checkpoint precision, quantizer, format and mixed bit widths remain separate
StorageHF shared inode-backed blobs are de-duplicated for physical disk accounting

Metadata-only Hugging Face cache entries are not reported as installed models. Remote enrichment is cached and offline tolerant.

04 · Serving

Compose Builder

The builder combines model metadata with target-node capacity and produces a reviewable Compose plan.

Collision-aware ports

Preferred ports are checked against saved deployments and real host bind availability. A free replacement is selected when necessary.

DGX-aware planning

Unified-memory reserve, context, checkpoint size, quantization and runtime overhead feed the fit estimate.

Quantization

Base dtype and checkpoint precision are distinct. vLLM normally relies on checkpoint auto-detection.

Plan integrity

The browser can review/copy generated YAML, but normal save does not accept arbitrary edited Compose from the client.

The memory estimate is a planning aid. Actual KV-cache/runtime usage depends on architecture, context, concurrency and engine implementation.
05 · Lifecycle

Deployment operations

Saving creates compose.yaml and deployment.json. It does not start a container.

Managed stacks can be validated, started, stopped, logged and archived. Archive runs Compose down for that managed project and moves the stack metadata/YAML into the archive directory; model checkpoints remain untouched.

Stop applies only to v2-managed Compose deployments. An external vLLM or ComfyUI can be shown as Online without exposing a destructive Stop action.
06 · Routing

LiteLLM stays the unified gateway

The Routing page can read active models from /v1/models, display a redacted local config, maintain an Ollama wildcard and add/remove routes for supported generated deployments.

Protected LiteLLM endpoints

If LiteLLM requires authentication, setup can copy only LITELLM_MASTER_KEY into a root-owned systemd credential for Model Manager:

LoadCredential=litellm_master_key:/etc/dgx-model-manager-v2/litellm_master_key

The broader LiteLLM environment file does not need to be readable by the Model Manager service user. The key stays server-side and is used for authenticated health/model requests.

Redaction

API keys, master keys, password/secret/authorization/credential fields and true token fields are redacted before the config reaches the browser. Benign fields such as max_tokens remain visible.

07 · Compatibility

Legacy scripts are opt-in

Existing start_*.sh files are never removed. Settings can enable Legacy Script Mode to expose them while you migrate. Once enabled, remember that the script content is arbitrary code executing as the Model Manager service user.

Do not enable Legacy Script Mode for scripts you have not reviewed and trusted.
08 · Access

Accounts, roles and tokens

RoleObserveOperateAdminister
ViewerYesNoNo
OperatorYesYesNo
AdminYesYesYes

The first Admin requires a one-time token generated locally by setup. Passwords are Argon2id-hashed. Browser sessions use opaque HttpOnly cookies and CSRF tokens.

Lockout protection is enforced server-side: an Admin cannot disable their own active account, and the last active Admin cannot be disabled or demoted. The UI mirrors these rules and marks the signed-in account as You.

API tokens are shown once and cannot exercise authority above their owner's current effective role.

09 · Security

The LAN is not a trust boundary

Authenticated reads

Inventory, host information, logs, routes and configuration require authentication.

HTTPS-first

Non-loopback HTTP is rejected by default.

SSRF policy

Private/loopback service targets are the default; unsafe/public targets are blocked unless policy changes.

Compose boundary

Client-modified YAML is not accepted by the normal generated-plan save path.

Workload ownership

External services are observable but cannot be stopped merely by matching a conventional port.

Secret isolation

Runtime config, DBs, TLS keys, environment files and tokens are excluded from publication.

10 · Cluster

Optional multi-node agents

The manager host is the local node and needs no agent. Additional DGX Spark systems can run the restricted node agent:

bash setup-agent.sh

The agent exposes node information, metrics, inventory, Compose generation and managed Compose lifecycle endpoints. It does not provide a general remote shell.

Use normal CA verification when possible. Self-signed operation requires explicit SHA-256 certificate fingerprint pinning when normal verification is disabled.

The local-node path was hardware-tested for 2.0.0. Remote operation against a second physical DGX Spark was not available during the release acceptance run and remains a field-validation area.
11 · Migration

What the importer changes

The importer can copy compatible service URLs, HF/LiteLLM paths and custom inventory directories into v2. It detects legacy scripts and can enable Legacy Script Mode so existing launch profiles remain visible during validation.

It does not alter v1, does not move checkpoints, and does not merge the v2 database/TLS identity into the old app.

12 · Promotion

Replace the old app only after acceptance

# Dry run
bash scripts/promote_v2.sh --target /path/to/current/DGX-Model-Manager

# Execute after review/testing
bash scripts/promote_v2.sh \
  --target /path/to/current/DGX-Model-Manager \
  --execute

The execute path requires typing PROMOTE-V2. It creates timestamped application/service backups before replacing the production application. Keep those backups until post-promotion testing is complete.
